# M9.2.1 Garmin Connect Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Garmin Connect as the primary, opt-in FIT import provider while retaining Intervals.icu and the shared FIT importer.

**Architecture:** A Garmin Personal API client handles credentials, bounded HTTP and pagination; `GarminActivityImportSource` adapts it to the existing source interface. A dedicated sync service imports bounded ZIP-extracted FIT streams through `ImportService`, uses existing external-ID mappings, and persists only sync progress/status. Garmin and Intervals.icu use distinct source injection and only one provider may be configured for automatic sync at a time.

**Tech Stack:** Java 21, Spring Boot, `java.net.http.HttpClient`, Jackson, JDBC/Flyway, Vue 3/TypeScript/Vitest, Playwright, Docker Compose.

**Spec:** User-provided M9.2.1 requirements; M9.1 evidence: `docs/research/m9.1-garmin-poc.md`.

## Global Constraints

- Garmin is disabled by default; use only `GARMIN_PERSONAL_API_KEY` for the backend key.
- Tokens are memory-only, never logged, persisted, returned, or sent over redirects.
- Garmin remains a FIT-only provider; all stored measurements come from the existing FIT parser.
- Do not overwrite or delete existing activity data; do not transfer real activity/FIT/GPS data to external services.
- Preserve Intervals.icu behavior; prevent ambiguous `ActivityImportSource` injection and competing automatic provider syncs.
- Bound HTTP responses, page count, ZIP size and extracted FIT size; never treat incomplete pagination as a successful window.
- Database changes are additive Flyway migrations only; all tests use the isolated `running_dashboard_e2e` database.
- No production deployment, secret, force-push, or merge.

## Review Focus

- HTTP 401 retry once after refreshing a token; repeated 401, 403, 404, 429/`Retry-After`, 5xx, timeouts and malformed/oversized responses fail safely without leaking response bodies or secrets. Test in client tests.
- Page cap reached while a page remains: surface incomplete sync and do not advance the persisted checkpoint. Test in client and service tests.
- ZIP path traversal, invalid archives, multiple FITs, oversized decompression and non-FIT entries: reject without extracting to disk. Test in ZIP processor tests.
- A FIT match with zero or multiple local candidates, or a Garmin ID already mapped elsewhere, must not be linked incorrectly. Test with repository-backed sync tests.
- Concurrent/manual/automatic sync and dual-provider configuration must not launch competing jobs. Test service concurrency and Spring configuration.

## Security and Data Integrity

All API keys enter only through backend environment/configtree secret. Tokens stay in memory, with redirects disabled and all errors sanitized. HTTP, pagination and ZIP processing are bounded. FIT import remains the sole writer of activity data; external IDs are linked only after an unambiguous shared importer result. The migration stores only provider sync metadata and does not rewrite existing rows.

## Failure Handling

Auth, malformed response, pagination truncation, ZIP validation, network, import and mapping errors are represented by sanitized error codes. 429 pauses subsequent sync until a clamped upstream delay (or configured interval); a failure or incomplete page sequence cannot advance last-success state. One activity's failure does not block later independent activities, except when global rate limiting or unsafe/incomplete listing requires stopping.
