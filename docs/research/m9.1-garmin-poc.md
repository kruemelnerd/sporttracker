# M9.1 – Garmin Connect Personal API PoC

**Reviewed:** 2026-11-08
**Scope:** source review and isolated command-line probe only. No production synchronization, database, or import changes.
**Live test status: BLOCKED** — no local Garmin Personal API key was available. No real Garmin activities were requested, and no mocked response is treated as a live result.

## 1. Executive summary

Garmin documents a Personal API for an individual Garmin user's own data. The API uses a Personal API key to issue a bearer token, supports paginated activity search, activity JSON detail, and an original activity-file download as ZIP. Garmin's documentation does not establish in the material reviewed whether every archive contains FIT, the JSON field schema, API quotas, historical retention, or how edits/deletions are surfaced.

Sporttracker already has the main reusable piece for a future integration: `GarminFitFixtureAdapter.decode(InputStream)` with FIT SDK `com.garmin:fit:21.221.0`. The Intervals.icu sync already downloads FIT and routes it through `ImportService.importFit`, then maps provider IDs. A production Garmin service is not justified by this PoC. A provisional M9.2 direction is Garmin as the primary pull source, retaining Intervals.icu as an optional complement only for fields verified to be absent from Garmin and actually consumed by Sporttracker; otherwise prefer Garmin alone to avoid needless duplicate traffic.

The local probe is deliberately separate: Python standard library, no application startup/database, no scheduler, environment-only key, files confined to Git-ignored `backend/data/garmin-poc/`, and a test-classpath Gradle command to inspect downloaded FIT through the existing decoder. The synthetic local FIT test validates parser reuse, not Garmin data quality.

## 2. Garmin Personal API functions reviewed

The Personal API page gives the token-exchange example. The official Swagger page is an interactive reference; Garmin's own published Personal API Python client was used to corroborate its activity route wrappers. The probe uses only these documented routes:

| Purpose | HTTP route | Documented behavior |
|---|---|---|
| Obtain bearer token | `POST /personalapitoken-service/personal-api/personal-api-key/token` | `Authorization: ApiKey …`; token returned as response text in Garmin's published client |
| Search activities | `GET /activitylist-service/activities/search/activities` | Summary list; `start`, `limit`; optional `startDate`, `endDate`, `activityType` |
| Activity detail | `GET /activity-service/activity/{activity_id}` | Individual activity JSON |
| Download original | `GET /download-service/files/activity/{activity_id}` | Original activity file returned as ZIP bytes |

The endpoint reference is not evidence that a particular user's account has data or that every file uses FIT. The probe requests only the first activity page, capped at 10 and defaulting to 3. It lists archive entries and processes `.fit` entries only when actually present and valid. No undocumented endpoint or reverse engineering is used.

## 3. Authentication and prerequisites

- Create a Personal API key in Garmin Connect Personal API settings. Garmin displays it once; the user chooses an expiration of 30, 90, 180 days, or one year. The expiry date/status can be viewed in Garmin Connect, and Garmin says it emails a reminder about a week before expiry.
- The key is sent only in the token request's `Authorization: ApiKey …` header. It is not itself a bearer token.
- Garmin FAQ states bearer tokens are valid for 24 hours or until the API key expires, whichever comes first. No refresh token is supported; request a new token with the key.
- Invalid key/API-key expiry HTTP behavior and precise response schema are not guaranteed in the public FAQ. The probe surfaces only HTTP status (not response body) and does not retry automatically.
- Credentials are read from `GARMIN_PERSONAL_API_KEY`. Set it through a local secret manager or protected environment; do not enter it in chat, a command argument, or a committed file. The token remains in process memory and is not logged or written.
- A live call also requires network access to Garmin and a valid, active key. Neither key setup nor live calls were performed for this report.

## 4. PoC description and local rerun

Files: `tools/garmin-poc/garmin_poc.py`, its README and offline unit tests. It calls the documented token, activity-search, per-activity-detail, and download routes; stores JSON and ZIP/FIT artifacts locally; reports status, content type/length, and counts without printing IDs, filenames, bodies, or credentials. Network/HTTP failures are sanitized. Responses and FIT entries have a 100 MiB limit; output is constrained to `backend/data/garmin-poc/` (directory mode `0700`, files `0600`). It does not open a database or invoke application import.

1. Create a Garmin key as described above and expose it locally as `GARMIN_PERSONAL_API_KEY` without putting it in shell history.
2. From the repository root run `python3 tools/garmin-poc/garmin_poc.py --limit 3`. Optional documented search parameters are `--start` (zero-based page offset), `--start-date`, `--end-date`, and `--activity-type`; `--limit` accepts 1–10 and each run reads one page.
3. Inspect a downloaded file using the existing decoder: `cd backend && ./gradlew inspectGarminPocFit -PfitFile=data/garmin-poc/<activity-id>-<filename>.fit`.
4. Compare saved local activity JSON with the parser's text summary manually. Do not copy real activity responses, FIT, or GPS into Git or send them to other services.

Offline unit tests use synthetic local responses to test code paths only. They are not mocked proof of Garmin availability.

## 7. Existing pipeline, provenance, and deduplication

### FIT and persistence inventory

`GarminFitFixtureAdapter` subscribes to FIT `SessionMesg`, `RecordMesg`, and `LapMesg`; it registers `ActivityMesg` but deliberately ignores it. It reads:

- **Session:** sport/sub-sport, UTC start, elapsed and timer (moving) seconds, distance, average speed, average/max HR, average running cadence (fallback to cadence), ascent and calories.
- **Record:** timestamp, distance, latitude/longitude (FIT semicircles converted to degrees), enhanced altitude/speed preferred over standard, HR and cadence. Elapsed time is derived from record timestamp minus session start; per-record descent is derived from altitude changes.
- **Lap:** sequence number, elapsed duration, distance, average speed, HR, cadence, ascent and descent.

It requires exactly one complete session. It does not currently inspect all FIT messages/fields, e.g. power, developer fields, device metadata, event/autopause semantics, advanced running dynamics, or Training Effect/load fields. These are parser gaps only where a FIT file actually contains the corresponding data; not all devices/files will.

`activity` stores sport/sub-sport, start, elapsed/moving seconds, distance, average speed, average/max HR, average cadence, ascent, calories. `activity_record` stores UTC record time, elapsed/distance, GPS, altitude, speed, HR, cadence and derived descent. `lap` stores duration, distance, speed, HR/cadence and ascent/descent. Average pace is derived from speed or distance/time for display; dashboard pace is derived from total time/distance. No training zones/load/VO2max/power metric or per-field origin is stored.

FIT duplicate protection checks SHA-256 first, then candidates by exact sport and start timestamp plus elapsed tolerance 2 seconds and distance tolerance 5 metres; multiple matches are treated as ambiguous. `activity_import_source` has unique `(provider, external_id)` mapping. Intervals sync checks this mapping before downloading; then imports FIT, links new or matched activities, and does not overwrite an existing activity. This identifies import source but not the origin/calculation method for each metric.

### Intervals.icu sync behavior

`IntervalsIcuClient` uses Java `RestClient` with Basic auth, fetches `GET /api/v1/athlete/0/activities` with oldest/newest date filters and downloads `/api/v1/activity/{id}/file`. The source adapter returns only ID/type for discovery, then transfers the downloaded FIT to the shared importer. The scheduled trigger runs at configured interval (default 15 minutes); sync uses an initial lookback, then a rolling 14-day overlap. Status, timestamps, result counters and retry-after are in memory (not durable). It handles no-file, malformed gzip/FIT, duplicate/ambiguous matches, upstream errors and rate limiting; it does not process provider JSON metrics or propagate remote edits/deletions.

## 8. Data quality and operational suitability

1. **Are Garmin API FIT files more complete than existing FIT?** Unknown until the same real activity is compared. The endpoint is documented as an original activity-file ZIP, but archive contents/record completeness are account- and activity-dependent and not live-verified.
2. **Does Garmin JSON add useful metrics?** An activity summary/search and individual detail route are documented, but field names and additional training metrics were not verified. The Garmin reference also lists separate wellness endpoints, which are outside this activity PoC and not evidence that they belong in Sporttracker.
3. **What can existing FIT provide?** Current parser already reads the session/record/lap values listed above; parser coverage, not source, is the immediate limitation for FIT-encoded fields.
4. **Which values are Garmin-only?** None can be classified from this blocked run. Later live comparisons should mark each as device-originated, Garmin-calculated, Intervals-calculated, FIT-derived, Sporttracker-calculated, or absent.
5. **What does Intervals.icu add today?** Its sync obtains FIT and maps its external activity ID; Sporttracker currently ignores Intervals activity JSON summary fields. Any additional Intervals-derived metrics need separate proof and implementation.
6. **Duplicate handling:** Use provider-specific external IDs as first idempotency key, then existing FIT hash and conservative activity matching as fallback. Cross-provider source IDs should map to one local activity. Preserve conflicts/ambiguous matches for review; do not silently merge by date/name alone.
7. **Regular pull:** Technically feasible from documented pagination and date/type filters, but quotas, backfill limits, change/deletion notices and outage behavior are unspecified. A bounded recent-window pull with overlap, explicit `429` handling/backoff and manual backfill is prudent; exact cadence needs live testing.
8. **Changes/deletions:** No documented update/delete semantics confirmed. M9.2 should treat remote changes as reconciliation candidates, preserve local records, record last-seen/source snapshots or hashes, and avoid destructive deletion absent an explicit policy.
9. **Reuse:** Add a Garmin `ActivityImportSource` adapter that retrieves the file and supplies it to `ImportService.importFit`; reuse parser, hash/measurement dedupe, and source-ID mapping. Keep provider JSON normalization separate until demonstrated useful. The M9.1 PoC itself does not alter production classes.

Resource cost is low for a single-user local server if sync stays bounded and sequential; API dependence and missing documented quotas remain the main reliability risks. FIT archive/JSON sizes and actual cadence are unmeasured.

## 9. Architecture variants and M9.2 recommendation

| Variant | Completeness | Effort / maintainability | Reliability / dependency | Privacy | Duplicates | Proxmox resources |
|---|---|---|---|---|---|---|
| **A. Garmin primary** | FIT baseline plus whatever live Garmin JSON proves useful; currently unverified | Lowest ongoing integration count; one provider path | Direct Garmin dependency; quota/change semantics unknown | One external provider | Lowest if Intervals sync disabled; source-ID + FIT dedupe still needed | Lowest request and service overhead |
| **B. Garmin + Intervals parallel** | Potentially broadest, but no measured unique fields in this run | Highest; two syncs, two failure/status paths and provenance reconciliation | Depends on two APIs and compounds outages/rate limits | Sends account/activity data to two configured providers | Highest; overlapping records from both providers | Modest absolute load, unnecessary traffic likely |
| **C. Garmin primary, Intervals supplemental** | Potentially broad, only if concrete unique fields are demonstrated | Medium/high; provider-specific enrichment and per-field provenance required | Garmin remains primary dependency; Intervals adds a second optional dependency | Two external providers for selected enrichment | Moderate; must map both IDs to one activity | Modest if enrichment is targeted and bounded |

**Provisional recommendation: A for M9.2's first implementation, with the existing Intervals.icu integration left available but not run in parallel by default.** Current evidence shows Intervals sync contributes FIT plus source ID, not imported JSON-derived metrics, while Garmin also documents an original activity download. No additional Intervals metric has been demonstrated in this PoC, so building C now would be speculative. First M9.2 should implement the same FIT import-source seam and verify three real activity cases; promote to C only if those comparisons identify an actual useful Intervals-only field. This recommendation is provisional because no live Garmin result confirms FIT availability/quality.

Future source provenance should at minimum record provider external IDs and source-file hash (already supported), then add per-field provenance only for normalized non-FIT metrics: `device/FIT`, `Garmin-calculated`, `Intervals-calculated`, or `Sporttracker-derived`. Store canonical values and calculation/source metadata, not formatted strings. Do not overwrite device data with a computed/provider estimate without retaining both origin and method.

## 10. Open questions and risks

- What actual fields and units do this user's activity-search and detail JSON contain? Are activity IDs always numeric `activityId` values?
- Does the user's downloaded ZIP contain FIT for all relevant activities, including older files and edited activities?
- What are Garmin's account/API request limits, backfill window, and behavior for edits/deletions or revoked/expired keys?
- Are `401`, `403`, `404`, and `429` response shapes/statuses consistent enough to define retries and operator messages?
- Do three same-activity comparisons show Garmin JSON or Intervals.icu data not available in FIT, and are any such metrics worth persisting?
- Which provenance granularity is justified for M9.2 without adding unnecessary schema complexity?
